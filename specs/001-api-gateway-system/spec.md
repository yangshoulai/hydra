## 用户场景与测试 *(mandatory)*

### 用户故事 1 - 稳定的大模型 API 调用 (优先级: P1)

开发者在使用多个第三方大模型渠道时,需要一个稳定可靠的代理服务,能够在某个渠道或 Key 失效时自动切换到其他可用资源,而不需要手动干预或重试。

**为什么是 P1**: 这是系统存在的核心价值 - 提供比直接调用上游更稳定的服务体验。没有这个功能,系统就失去了存在意义。

**独立测试**: 配置多个渠道和 Key,模拟其中一个失败,验证请求能自动路由到其他可用渠道并成功返回结果。

**验收场景**:

1. **Given** 配置了 3 个渠道,每个渠道有 2 个 API Key, **When** 用户发起 `/v1/chat/completions` 请求, **Then** 系统成功返回 AI 响应,TraceID 记录在日志中
2. **Given** 渠道 A 的 Key-1 返回 401 错误, **When** 用户再次请求, **Then** 系统自动使用渠道 A 的 Key-2 重试并成功,Key-1 被永久禁用
3. **Given** 渠道 B 返回 HTTP 200 但 Body 包含 "无可用后端" 错误文本, **When** 用户请求, **Then** 系统识别为假成功,自动切换到渠道 C 重试,用户不感知错误
4. **Given** 渠道 C 连续 3 次返回 500 错误, **When** 用户第 4 次请求, **Then** 该渠道进入熔断状态(冷却中),系统路由到其他渠道
5. **Given** 用户请求模型 `gpt-4`, **When** 系统内部配置将其映射到上游的 `vip-gpt4-0613`, **Then** 请求被正确重写并发送到上游,响应返回时模型名恢复为 `gpt-4`

---

### 用户故事 2 - 低成本的渠道管理与配置 (优先级: P2)

管理员需要通过 Web 界面轻松添加、编辑、测试多个上游渠道,并能自动发现和同步上游模型列表,避免手动维护复杂的模型名称映射关系。

**为什么是 P2**: 没有便捷的管理界面,配置和维护成本极高,但核心代理功能(P1)可以先通过配置文件或数据库直接操作实现。

**独立测试**: 在 Web 界面添加新渠道,点击"同步模型"按钮,验证能看到上游模型列表并完成映射配置,保存后能在代理请求中生效。

**验收场景**:

1. **Given** 管理员登录管理后台, **When** 点击"添加渠道"并填写名称、BaseURL、API Keys, **Then** 渠道保存成功并显示在列表中
2. **Given** 渠道已保存, **When** 管理员点击"同步模型"按钮, **Then** 系统调用上游 `/v1/models` 接口,展示差异对比表格(新增、缺失、存量)
3. **Given** 同步结果显示 5 个新增模型, **When** 管理员为新模型配置统一名称(如 `gpt-4-turbo`)并设置权重, **Then** 配置保存后,代理请求可以使用新模型
4. **Given** 渠道配置有 10 个 Key, **When** 管理员点击"立即测活", **Then** 系统并发测试所有 Key,显示健康状态(Active/Dead/Cooling),标记失效的 Key
5. **Given** 上游已下架某个模型, **When** 管理员同步模型, **Then** 差异表格标红显示"缺失模型",管理员可选择删除或保留本地配置

---

### 用户故事 3 - 问题排查与审计 (优先级: P3)

运维人员在用户报告问题时,需要通过管理后台快速检索请求日志,根据 TraceID 定位具体请求的完整链路信息(使用了哪个渠道、哪个 Key、耗时、错误信息)。

**为什么是 P3**: 日志是运维必需,但系统可以先在文件中记录,通过命令行工具查询。UI 检索是体验优化,不影响核心功能交付。

**独立测试**: 模拟一次失败请求,在管理后台日志页面通过 TraceID 搜索,验证能看到完整请求元数据和错误信息。

**验收场景**:

1. **Given** 用户报告某次请求失败, **When** 运维人员在日志页面输入 TraceID 搜索, **Then** 显示该请求的渠道、模型、状态码、耗时、错误信息
2. **Given** 日志列表显示过去 7 天的请求, **When** 运维人员筛选"状态=失败"且"渠道=渠道 A", **Then** 只显示符合条件的日志,按时间倒序排列
3. **Given** 某个请求记录显示"HTTP 200 但被嗅探器拦截", **When** 运维人员点击详情, **Then** 显示原始响应 Body(假 200 的错误文本)和重试记录
4. **Given** 系统运行超过 30 天(默认日志保留期), **When** 自动清理任务执行, **Then** 超过 30 天的日志被物理删除,数据库执行 VACUUM 释放空间
5. **Given** 调试模式启用, **When** 任何请求出错, **Then** 完整的 Request/Response Body 写入文件日志,可通过 TraceID 关联审计日志

---

### 用户故事 4 - 实时监控与健康可视化 (优先级: P3)

管理员需要在仪表盘上实时看到系统的关键指标(QPS、成功率、各渠道健康状态),以便快速发现和响应异常情况。

**为什么是 P3**: 监控仪表盘是运维体验优化,系统可以先通过日志和命令行工具监控,仪表盘可以在后续阶段添加。

**独立测试**: 在仪表盘查看 QPS 波形图和渠道健康墙,模拟一个渠道进入熔断状态,验证状态实时更新。

**验收场景**:

1. **Given** 管理员打开仪表盘, **When** 系统有请求流量, **Then** QPS 波形图实时更新,显示过去 1 小时的请求量变化
2. **Given** 仪表盘显示今日成功率 98%, **When** 某个渠道大量失败导致成功率降至 85%, **Then** 成功率指标实时更新并高亮异常
3. **Given** 健康墙显示所有渠道状态, **When** 渠道 B 进入熔断状态(冷却中), **Then** 该渠道卡片显示为黄色警告状态,标注冷却剩余时间
4. **Given** 某个渠道的 10 个 Key 中有 3 个已死, **When** 管理员查看渠道列表, **Then** 显示 "Keys: 7/10",点击可查看详细 Key 状态
5. **Given** 系统检测到所有渠道都不可用, **When** 仪表盘刷新, **Then** 显示红色严重警告,提示"无可用渠道"

---

### 边界情况

- **所有渠道/Key 全部失败时**: 系统返回明确的 503 错误,错误信息提示"当前无可用上游渠道,请联系管理员",记录到审计日志
- **上游返回超大响应 Body (>10MB)**: 系统限制响应大小,超过限制返回 413 错误,避免内存溢出
- **SSE 流式响应中途断流**: 检测到上游断开连接,记录错误日志,客户端收到不完整响应(由客户端处理重试)
- **并发请求超过系统处理能力**: 使用请求队列缓冲,超过队列长度返回 429 错误,建议客户端稍后重试
- **渠道冷却期结束后的探测请求失败**: 继续保持熔断状态,重置冷却时间,避免频繁探测浪费资源
- **模型名映射冲突(多个上游模型映射到同一统一名)**: 系统按权重和优先级选择渠道,支持多个上游模型共享统一名称
- **用户请求的模型在所有渠道都未配置**: 返回 404 错误,错误信息提示"模型 xxx 不存在",建议管理员检查配置
- **数据库文件损坏或锁定**: 系统启动时检测数据库健康状态,损坏时拒绝启动并提示管理员恢复备份
- **日志写入失败(磁盘满)**: 降级为仅输出到标准错误流(stderr),不阻塞代理请求处理,同时发出告警

## 需求 *(mandatory)*

### 功能需求

#### 核心代理与路由

- **FR-001**: 系统必须支持 `POST /v1/chat/completions` 接口,兼容 OpenAI API 格式,支持 SSE 流式响应
- **FR-002**: 系统必须支持 `GET /v1/models` 接口,返回虚拟模型列表(所有系统配置的统一模型名)
- **FR-003**: 系统必须支持多渠道配置,每个渠道包含 BaseURL、API Key 池、优先级、权重
- **FR-004**: 系统必须支持模型名称重写,将用户请求的统一名称(如 `gpt-4`)映射到上游真实名称(如 `vip-gpt4-0613`)
- **FR-005**: 系统必须实现负载均衡,根据权重和优先级在多个可用渠道间分配流量
- **FR-006**: 系统必须支持 Key 池化管理,单渠道支持配置多个 API Key,自动轮询使用

#### 熔断与韧性

- **FR-007**: 系统必须区分硬故障(401/402/403/429 quota)和软故障(5xx/timeout/429 rate limit),单个请求的最大重试次数默认为3次,可通过系统设置配置
- **FR-008**: 硬故障必须永久禁用对应 Key,立即切换到其他 Key 重试,不自动恢复(需人工重置)
- **FR-009**: 软故障必须实施熔断机制,连续失败达到阈值(默认 3 次)后进入冷却状态(默认 60 秒)
- **FR-010**: 冷却期结束后必须进入半开(Half-Open)状态,允许 1 个探测请求,成功则恢复,失败则重新冷却
- **FR-011**: 系统必须分别维护 Key 级和 Channel 级的健康状态,Key 故障不影响同渠道其他 Key
- **FR-012**: 模型级故障(某模型在某渠道持续失败)必须单独熔断,不影响该渠道其他模型

#### 智能清洗与假 200 识别

- **FR-013**: 系统必须实现响应嗅探器,识别 HTTP 200 中的错误响应
- **FR-014**: 嗅探规则必须覆盖: JSON 中包含 `"error"` 字段、HTML 响应(如 `<!DOCTYPE html>`)、明文错误(如 "无可用后端"、"额度不足"、"maintenance")
- **FR-015**: 识别为假 200 的响应必须拦截,视为软故障处理,自动重试其他渠道,不透传给客户端
- **FR-016**: 假 200 拦截事件必须记录到审计日志,标注"嗅探器拦截",便于运维分析上游渠道质量

#### 模型同步与漂移检测

- **FR-017**: 系统必须支持从渠道的 `/v1/models` 接口自动发现上游模型列表
- **FR-018**: 系统必须提供差异比对功能,计算新增模型(上游有本地无)、缺失模型(本地有上游无)、存量模型(两边都有)
- **FR-019**: 差异结果必须在管理界面可视化展示,新增模型高亮,缺失模型标红
- **FR-020**: 管理员必须能在差异视图中配置新增模型的统一名称、权重、启用状态,一键应用变更

#### 全链路日志系统

- **FR-021**: 系统必须为每个请求生成唯一 TraceID(UUID 格式),贯穿整个请求生命周期
- **FR-022**: 系统必须维护双层日志架构: 审计日志(数据库)和调试日志(文件)
- **FR-023**: 审计日志必须记录: TraceID、请求时间、用户标识(Token/IP)、请求模型、真实模型、渠道 ID、状态码、耗时(ms)、简略错误信息
- **FR-024**: 调试日志必须记录: TraceID、完整 Request Body、完整 Response Body(仅错误请求或 Debug 模式启用时)
- **FR-025**: 审计日志必须支持 Web 界面检索,按 TraceID、时间范围、状态(成功/失败)、渠道筛选
- **FR-026**: 系统必须支持配置日志保留天数(默认 30 天),自动清理过期日志并执行数据库 VACUUM
- **FR-027**: 调试日志必须支持自动轮转切割,单文件大小限制(默认 100MB),保留最近 10 个文件

#### 管理后台功能

- **FR-028**: 系统必须提供 Web 管理界面,基于 Vue 3 + Naive UI,通过 Go Embed 打包到单一二进制文件
- **FR-029**: 仪表盘必须显示: QPS 实时波形图(过去 1 小时)、今日请求成功率、渠道健康墙(正常/熔断/禁用状态)
- **FR-030**: 渠道管理页面必须支持: 列表展示(含 Key 健康度统计)、新增/编辑向导、模型同步 Diff 视图、立即测活功能
- **FR-031**: 日志查询页面必须支持: 筛选器(时间/TraceID/状态/渠道)、列表展示、详情抽屉(含 TraceID 复制功能)
- **FR-032**: 系统设置页面必须支持: 熔断策略配置(失败阈值/冷却时长/最大重试次数)、日志保留时长、访问令牌管理

#### 访问控制与安全

- **FR-033**: 系统必须支持访问令牌(Access Token)机制,客户端通过 `Authorization: Bearer <token>` 访问代理接口
- **FR-034**: 管理后台必须支持令牌的创建、查看、删除,令牌必须加密存储
- **FR-035**: 系统必须支持管理后台的独立认证机制,使用基于会话的用户名/密码登录,避免代理令牌被滥用访问管理接口
- **FR-036**: API Key 在管理界面和日志中必须完整显示(不脱敏),便于管理员识别和问题排查

### 非功能需求

#### UI/UX 体验标准

- **NFR-001**: 管理界面必须提供清晰的视觉层次,关键操作按钮(如"添加渠道"、"同步模型"、"立即测活")需在页面加载后 3 秒内被管理员识别
- **NFR-002**: 界面必须减少非必要装饰元素,数据表格和操作控件占据页面主要视觉焦点(至少 70% 可视区域)
- **NFR-003**: 色彩方案必须保持一致性,主色调不超过 3 种,确保视觉清爽且不造成认知负担
- **NFR-004**: 管理员完成常见任务(如查看渠道健康状态、搜索日志)时,页面交互步骤不超过 2 步
- **NFR-005**: 界面必须支持常见桌面分辨率(1920x1080、1366x768),关键信息在不同分辨率下无需横向滚动即可查看
- **NFR-006**: 所有异步操作(如模型同步、日志查询)必须提供可视化加载状态,用户在操作后 500ms 内看到进度反馈
- **NFR-007**: 错误提示必须清晰可读,避免技术术语,管理员能在 5 秒内理解错误原因并知道如何修复
- **NFR-008**: 表格数据必须支持排序和筛选,单页显示行数可配置(默认 20 行),超过限制时提供分页导航
- **NFR-009**: 关键状态变化(如渠道进入熔断、Key 被禁用)必须通过视觉高亮(颜色/图标)在 1 秒内吸引管理员注意
- **NFR-010**: 界面首次加载时间不超过 2 秒(不含数据请求),页面切换(如从仪表盘到渠道管理)响应时间不超过 500ms

### 关键实体 *(feature involves data)*

- **Channel (渠道)**: 代表一个上游大模型服务提供商,包含名称、BaseURL、优先级、权重、健康状态(Enabled/Disabled/Cooling)
- **Key (密钥)**: 归属于某个 Channel 的 API 密钥,包含密钥内容(sk-xxx)、状态(Active/Dead/Cooling)、失败计数、最后失败时间
- **ChannelModelConfig (渠道模型配置)**: 定义某渠道支持的模型及重命名规则,包含上游原始名称、统一映射名称、权重、启用状态
- **RequestLog (请求日志)**: 审计日志记录,包含 TraceID、请求时间、用户标识、请求模型、真实模型、渠道 ID、Key ID、状态码、耗时、错误信息
- **SystemSetting (系统配置)**: KV 格式存储系统配置,如日志保留天数、熔断阈值、冷却时长、最大重试次数
- **AccessToken (访问令牌)**: 客户端访问代理接口的凭证,包含令牌名称、令牌值(加密)、创建时间、最后使用时间
- **AdminUser (管理员用户)**: 管理后台登录用户,包含用户名、密码哈希、会话信息、创建时间、最后登录时间

## 成功标准 *(mandatory)*

### 可测量结果

- **SC-001**: 用户通过代理调用大模型接口,在至少 1 个渠道可用的情况下,成功率达到 99.5% 以上(排除所有渠道都不可用的情况)
- **SC-002**: 当某个 Key 失效时,系统在 1 秒内自动切换到其他可用 Key,用户感知延迟不超过请求超时时间的 10%
- **SC-003**: 假 200 响应(错误文本/HTML)的识别准确率达到 95% 以上,通过人工抽样 100 个拦截记录验证
- **SC-004**: 管理员在 Web 界面完成"添加新渠道 + 同步模型 + 配置映射"的完整流程,耗时不超过 5 分钟
- **SC-005**: 模型同步功能能在 10 秒内完成与上游的差异比对,并在界面展示结果(假设上游响应时间 < 3 秒)
- **SC-006**: 审计日志查询支持通过 TraceID 在 100 万条记录中检索,响应时间不超过 2 秒
- **SC-007**: 系统在 1000 QPS 并发请求下,平均响应时间不超过上游响应时间 + 50ms(代理层开销 < 50ms)
- **SC-008**: 日志自动清理任务能在 10 分钟内完成 30 天前数据的删除和数据库压缩(假设日志量 < 1000 万条)
- **SC-009**: 仪表盘的 QPS 波形图延迟不超过 5 秒,渠道健康状态变更在 10 秒内反映到界面
- **SC-010**: 系统支持单个二进制文件部署,启动时间不超过 5 秒,配置文件不超过 3 个(数据库文件、配置 YAML、日志文件)
- **SC-011**: 管理员首次访问管理界面时,在 5 秒内能识别出关键功能区域(仪表盘、渠道管理、日志查询、系统设置)的位置
- **SC-012**: 在用户调研中,90% 的管理员能在不阅读文档的情况下,在 3 分钟内完成首次渠道添加任务
